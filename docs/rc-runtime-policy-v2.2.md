# RC 运行协议 v3.0

> 更新：2026-09-29。沿用 v2.2 文件名。本文件是资源发现、委派、前端交付、测试和安全专项的唯一执行规范。启动时了解各节，执行具体任务时重点读取相关小节；不要把全文复制给每个子任务。

## 1. 启动与恢复

“执行 Gate 0 Bootstrap”兼容旧口令，含义改为轻量启动，不要求生成全套 Gate/Wave 文档。

1. 定位通用规则、项目交接、资源记录及已有任务状态。项目内标准位置为 `docs/`，也支持根目录或用户指定位置；以实际找到且有效的一份为准。发现多份互相冲突时先报告差异，不静默选旧版。没有交接文件也可依据明确需求进行有限工作。
2. 查看工作目录、Git 状态、未提交改动、项目启动方式和本次涉及的代码。读取旧项目的已有设计、截图、已通过证据和 WIP，避免从零重做。
3. 按第 2 节发现资源。信息不足时继续不依赖它的审计；不得给未知或已耗尽资源派实际任务。
4. 给出最小任务边界：目标、保留行为、完成条件、主要风险、相关测试目标。需要时做短小可审查的架构决定，不按角色数量拆工作。
5. 选择一个可交付增量，直接实施或按第 3 节委派。已确认 UI 图进入第 4 节；无需 UI 的任务跳过该节。
6. 从启动起标记“安全专项：待执行/已有基线待核验”，在本轮项目交付或发布前按第 6 节完成；不得只写“以后补”。

旧项目正常行为是回归基线。避免无关重构，不覆盖其他窗口未完成改动。缺少运行环境时明确哪些结论只能由代码审查支持。

## 2. 资源发现与任务路由

### 2.1 用户提供什么，RC 调查什么

- 用户仅需说明已拥有的订阅或服务。已有记录直接复用，不重复要求填写模型能力清单。
- RC 主动查官方套餐说明、模型文档和客户端文档：当前型号、视觉输入、图像/视频生成、编程客户端、浏览器、子智能体、上下文、入口、用量规则、适用地区、套餐与 API 边界。记录来源与核实日期；冲突或不能确认处保留未知。
- 只调查与近期任务有关的资源，首次建档后增量维护；恢复旧项目、订阅变化、模型变更、限流或额度异常时刷新有关项，不每轮重查全网。
- 通过已授权且实际可用的工具核实客户端版本、连接状态和账号用量。不能读取的私有信息，仅在影响当前安排时定点询问；不扫描或输出凭据来推测权限，不编造剩余额度。
- 网页功能、客户端工具、API 权益分开记录；某供应商有一个模型不等于用户订阅包含它。已有订阅不自动授权额外付费或购买服务。

### 2.2 最小资源记录

项目使用一份 `docs/resource-profile.md`，可以从个人资源文件复制。每个近期会用到的资源记录：

`服务/套餐；平台或客户端及版本；具体模型/工具；适合的任务及依据；视觉/浏览器/委派通道；账号可用状态；额度及获知时间（未知也可）；已核实来源/日期；本项目表现；替代方案。`

能力状态必须区分：官方支持、客户端已接通、项目验证过、不可用、未知。额度未知不等于零，也不等于无限；在已确认账号和调用通道可用时可以小范围执行并观察限制。

### 2.3 分配规则

先检查任务所需能力和工具是否具备，再比较本项目质量、额度、速度和返工成本。官方能力和评测只提供候选依据；不能杜撰“某模型在某 Agent 最强”。必要时在一个真实小任务中校准，不另建冗长评测流程。

- 图像还原与视觉验收负责人必须实际看到参考图和浏览器渲染；不能仅靠 OCR、DOM 或模型自述证明具备视觉能力。
- 非视觉模型可承担已有明确规格的逻辑、接口和重复实现，由视觉负责人持续整合检查。
- 复杂旧项目实现允许使用能力匹配的强模型，不要求先让不合适的模型失败。
- 额度耗尽、套餐到期或工具失效时更新状态并转用已核实的替代方案；没有合适替代时只暂停受阻部分，说明缺口。
- 生图、生视频、研究、编程、截图检查均是可选资源。已有满意素材直接复用，不能为了使用权益增加步骤。

## 3. 执行与委派

默认主负责人直接推进。规则明确授权主动调用可用子智能体，但须遵守宿主权限、并发和模型限制；有收益才委派。

适合委派：独立代码区域调查、不同根因排查、明确边界模块、针对具体风险的审查。连续视觉微调、依赖未完成步骤或争用同文件的任务不要强行并行。

委派包可直接写在工具消息中，无需创建角色文件：

```text
任务/完成条件：
工作目录、代码基线与输入材料：
允许修改；禁止修改；与其他任务的依赖：
所需能力与已选可用模型（宿主支持时）：
要验证的问题与证据：
返回：改动/提交、检查结果、未验证项、遗留风险。
```

一个文件同一时刻只指定一个写入者。主负责人处理共享文件、合并和集成；不让用户在 Agent 之间搬运长上下文。平台不支持委派时采用单负责人或最少的人工跨平台任务，并说明实际限制。

失败先归因，发现能力不匹配可立即换人。连续修复没有减少问题时，停止同样的尝试，改查假设、环境或契约；只在真实产品取舍需要用户判断时升级给用户。

## 4. 前端：参考图 → 层级 → 真实页面 → 调节入口

### 4.1 已有图的项目

优先使用用户已确认的 UI 图；图中已有决定不再重新选稿。未确认方向只询问影响本轮的关键差异。缺失画面先复用已确认组件与样式，只有确实需要新视觉决策时才补图或交互原型。

“视觉方向确认”与“UI 施工准入”分开。前者是用户认可方向；后者是所做范围的结构和关键规则足够明确。可以先做有限代表页面来验证可实现性；代表页面不必等所有页面的长规格写完。主结构未理清前不得批量铺开。

### 4.2 先识别层级

视觉负责人先检查现有 DOM/组件/CSS 与参考图，在一份简短 `docs/design/ui-spec.md` 中记录：

- 页面包含关系：App Shell、导航、主内容、侧栏、卡片、卡片内内容；注明全局、页面或组件作用域。
- 布局关系：Grid/Flex、宽高范围、主次比例、gap、padding、对齐、响应式变化。
- 滚动与定位：谁滚动、谁固定、谁 sticky、遮罩和 Drawer 挂载在哪里，弹层打开时焦点与滚动如何处理。
- 视觉与堆叠：背景、表面、玻璃层、边框、内容、浮层的关系；检查实际 stacking context 和 overflow，不用无序增大 z-index 掩盖问题。
- 图中不能确定的交互和状态：优先沿用旧项目有效行为，注明假设；不把图片猜测写成用户决定。

记录应足够指导实现，不强制额外拆 component-tree、动效、状态等多个文件。各类 token 优先维护在项目已有的 CSS/主题配置中，避免文档与代码双份漂移。

### 4.3 先完成一个代表页面

在真实项目、真实组件限制下完成代表页面和关键状态，按“结构和层级 → 比例与滚动 → 交互状态 → 颜色、材质与动效”修正。与参考图对比时统一视口、缩放、主题和尽可能一致的数据状态；截图保留对应代码基线。

明显错位、错误包含关系、被遮挡按钮、溢出和不可用交互由负责人先修复。不要把这些缺陷打包成“请用户微调”。局部截图或图片差分是辅助证据，不能代替交互检查，也不要求无意义的像素完全一致。

### 4.4 项目内视觉调节面板（有前端视觉工作的项目必交）

由前端负责人在当前项目内实现轻量面板；已有等效入口可复用。不要求用户另开窗口制作工具。纯后端/命令行项目可注明无前端而不适用。

- 能选择页面板块，按“全局/当前页面/当前板块”和暗浅主题区分参数，明确继承与覆盖关系。
- 至少暴露本次相关的板块宽度/间距/内边距、背景色与透明度、玻璃模糊、边框、阴影、圆角；文字对比度、动效时长和浮层参数在本次涉及且安全时提供。参数有名称、单位、合理范围，约束不允许破坏关键布局与可访问性。
- 修改后在真实页面即时预览，提供默认值/当前值、撤销或重置、预设保存、JSON 导入导出；适用时支持复制 CSS Variables。
- 参数仅修改有白名单的视觉 token；禁止任意脚本/HTML/CSS 执行、任意文件写入、接口地址/权限/密钥修改。导入校验 schema、类型、范围和大小，拒绝未知危险字段。
- 使用 token 改样式，不让用户手工在多处代码复制参数。确认后由 Agent 导入预设并写回正式 token/配置，刷新和清空本地临时设置后验证结果仍存在。
- 默认只在开发或专门设计预览构建中启用，正常生产构建不包含调节入口和调试写入通道；隐藏按钮不等于移除能力。若用户另行需要生产主题编辑器，应作为独立功能设计服务端鉴权和权限。
- 交付说明入口如何打开、各参数影响什么、如何重置/导出/让 Agent 固化，以及哪些结构不建议调。面板入口放开发工具区或专用预览路由，不污染产品正常流程。

面板让用户调整偏好；基本还原、默认参数、可用性与视觉质量仍由负责人完成。

## 5. 有目标、有边界的验证

### 5.1 先写要回答的问题

每项检查记录：`目标/风险；场景与输入；预期行为或事先约定阈值；方法；代码基线/环境；实际结果与证据。`

检查目标来自需求、改动影响或真实风险。先复用已有检查；没有可检验目标、只证明实现细节或重复已有证据的测试不新增。可逆低影响样式调整一般不新增单元测试，做相关视口的视觉检查即可。

### 5.2 按改动选择证据

- 构建/类型/lint：说明能证明的技术范围，不能宣布功能或视觉正确。
- 功能：检验受影响用户路径及重要失败路径；涉及权限时至少有未授权拒绝场景，不能只测成功。
- 视觉：匹配视口/主题/状态，核对结构、包含关系、对齐、滚动、遮挡、材质和可访问性。无实际渲染或无看图通道时写“未做视觉验证”。
- 性能/可用性：先定义负载、持续时间、延迟/错误/资源阈值和停止条件，再做有界验证；无基线时先采集基线，不编造“优化了多少”。
- 安全：使用第 6 节的具体威胁场景和证据；扫描器没有告警不等于安全通过。

单次人工打开首页，只能证明已查看的该页面状态。不要遍历无关页面凑检查数量，不写“全都没问题”“全部安全”等超出证据的结论。

### 5.3 复用与复测

- 结果记录提交号；未提交改动使用 diff 指纹或等效可识别快照，同时记录依赖、环境、配置、相关数据状态与检查范围。
- 同一有效基线下复用生产者或 CI 的结果，RC 不默认再跑一遍。合并或修改后判断证据是否失效，只复测受影响范围；高风险共用基础改动可扩大回归。
- 不确定失败测试是否有效时，可用历史失败、修复前行为或简单受控负例证明它能发现目标问题，不为每个低风险改动引入变异测试。
- 检查失败由负责人修复后针对性复测。通过且无新增风险就进入下一任务，不继续无限扩测。
- 结论使用“通过/失败/未验证/不适用”，附范围和理由；异族审查不作为默认必经步骤。

例如“Context Panel 不遮挡输入框”应明确视口、面板开关和输入区可操作性；“用户 A 不能读取 B 的私聊”应检查服务端拒绝和无消息泄露。两者不能由一次 build 替代。

## 6. 每个项目必做的安全专项轮

### 6.1 何时与谁负责

每个项目都必须有明确安全负责人和一轮“识别攻击面 → 加固 → 验证 → 记录剩余风险”的专项工作，包括旧项目、原型和纯前端项目。不得以无后端、项目小、进度紧、额度不足、已有常规测试为由取消。

专项安排在代表路径或主要功能可运行后、本次最终交付/发布前；设计期发现的明显漏洞立即处理，不等专项轮。后续发布核对既有安全基线，对新增或受影响攻击面增量复核；不每改一个像素都重跑全套。

优先让有能力的安全子智能体或独立审查者找风险，由明确实施者加固。无法独立审查时主负责人仍完成专项并注明单人复核限制，不伪造审查者。安全负责人对下面每类作适用性判断，具体措施按真实攻击面选择，不盲目安装所有中间件。

### 6.2 最低覆盖范围

1. **DDoS / DoS / 资源滥用**：识别公开入口、登录、搜索、上传、WebSocket、AI 调用等高成本路径。适用时配置账号/IP/连接/操作维度限流、请求体与连接上限、超时、有界队列、并发预算和降级。多实例限流须考虑共享计数，客户端 IP 来源须有可信代理边界。公网容量型 DDoS 需要 CDN/WAF/云清洗、源站访问限制和告警等部署防护；应用限流或本地压测不能证明抗住公网 DDoS。
2. **缓存雪崩、击穿、穿透与故障**：先确认是否存在缓存及其用途。按风险采用 TTL 抖动、热点回源合并/有界锁、短期负缓存、超时与熔断、有界回退、预热及退避。验证集中失效和缓存不可用时数据库不会被无界打满；认证/权限数据不可因缓存失效而默认放行，陈旧数据回退需明确哪些业务允许。
3. **注入与不可信输入**：覆盖 SQL/NoSQL/命令/模板注入、XSS、路径穿越、危险上传和适用的 SSRF。使用参数化查询、上下文正确的输出编码、可靠清洗、输入白名单、路径与外连边界；不把前端校验当服务端防护。检查 Markdown、富文本、文件名和第三方内容的渲染。
4. **越权与数据隔离**：服务端逐次鉴权及对象/动作级授权，检查水平越权、角色提升、群/房间/租户隔离。URL、HTTP 方法、WebSocket 消息和下载入口都不能绕过；不能只隐藏按钮。成员移除、注销或权限撤销后，已有连接和会话也必须按规则失效。
5. **字典攻击、暴力破解、撞库与枚举**：检查登录、验证码、重置密码、邀请码与 token 等入口的速率与尝试次数。按风险采用账号和来源组合限流、渐进等待、通用错误信息、短期单次令牌、安全密码哈希及高风险账号 MFA。避免可被滥用的永久锁号造成拒绝服务。第三方身份认证需核实集成配置，不能直接当作全部已解决。
6. **会话、密钥和供应链**：检查 HTTPS、Cookie 安全属性、CSRF、CORS、会话/token 生命周期、权限最小化、服务端密钥、日志脱敏、依赖漏洞可达性和构建产物。开发调节面板、测试账号和调试端点不得意外进入生产。纯静态项目仍检查发布配置、依赖和敏感信息暴露。
7. **业务与 AI 风险（适用时）**：重复请求与状态越级、交易/投票幂等、上传滥用、AI 成本配额；提示注入不能越过服务端工具授权，用户内容不能泄露系统密钥、他人数据或游戏隐藏身份。跨用户缓存键与日志也需要隔离。

### 6.3 必须产生实际改进与验证

对发现的问题，在已授权范围内直接修复代码、配置或部署模板；不要只交一份建议报告。需要真实部署权限或额外付费设施时，先备好可审查配置、操作步骤、回滚和验证方法，再请求必要操作。现有防护充分时可以不做无意义改动，但必须提供核验依据。

验证在自有或明确授权的测试环境进行，使用合成账号与有限请求；定义请求量、并发、时长和停止条件。默认不向线上或第三方执行洪泛、真实密码字典破解或破坏性攻击。用少量受控失败请求验证阈值、锁定、授权和恢复；缓存故障在隔离环境注入。

至少把适用风险转为具体可证伪目标，例如：限流阈值后请求受控拒绝且正常用户仍可用；热键失效时回源并发有界；A 用户无法读取 B 对象；注入内容不被执行；少量错误口令触发预期保护。阈值根据项目容量和业务要求确定，不在模板中编造统一数字。

### 6.4 安全记录与发布判定

使用一份 `docs/security-review.md`，记录本轮基线/日期/负责人、各类适用性、已存在防护、实际修复、验证证据、未验证项、部署待办、风险级别、责任人和下一步。

- 单项状态：通过、失败、未验证、不适用（附攻击面依据）。不能把“没找到代码”“没有权限”记为不适用。
- 每轮区分“代码已加固”“测试环境已验证”“生产配置已核实”，不将部署模板存在等同上线生效。
- 已知严重/高危且可利用的问题未修复，或关键适用防护未验证时，发布状态为阻塞；不得用一份报告换取 PASS。
- 低风险残留写清影响和处理计划；需接受业务风险时由用户明确决定并留痕，不能静默接受。任何例外也不能取消安全轮或把未验证改成通过。
- 没有部署权限时交付可审核配置与待办，明确“部署安全未验证，发布条件未满足”。不声称全面安全或绝对防 DDoS。

技术参考（首次编写核实：2026-09-29；落地前结合实际技术栈核对官方最新文档）：[OWASP DoS](https://cheatsheetseries.owasp.org/cheatsheets/Denial_of_Service_Cheat_Sheet.html)、[身份认证](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)、[授权](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)、[注入预防](https://cheatsheetseries.owasp.org/cheatsheets/Injection_Prevention_Cheat_Sheet.html)、[缓存策略](https://learn.microsoft.com/en-us/azure/postgresql/development/how-to-cache)。这些是检查依据，不要求项目采用某家云服务。

## 7. 最少记录与交付

默认仅维护：

- `docs/project-state.md`：目标、当前任务/负责人、关键决定、基线、验证摘要、阻塞、下一步与安全状态。已有 task board 等文件能承担这些职责时继续使用，不再复制一套。
- `docs/resource-profile.md`：当前资源；只更新变化项。
- `docs/security-review.md`：安全专项开始时建立，后续增量维护。
- 前端任务才需要简短 `docs/design/ui-spec.md`；tokens、可调预设优先在代码中维护。

只有实际出现多人并行或长期复用需求才生成角色文件、单独任务板或 ADR。旧控制文件不删除，用清晰指针标注当前权威状态；不要每轮同步四五份重复记录。

普通交付直接说明“结果、验证范围、遗留项、下一步”。需要用户动作时才输出：

```text
需要你做的事及原因：
平台/入口（确有跨平台需求才开窗口）：
已经准备好的材料、参考图、提示词或配置：
最少操作：
结果保存位置/返回什么：
完成后我将继续做什么：
```

额度耗尽或长期暂停时，把未提交改动、已完成证据、受阻资源和恢复动作写进当前状态；无需再建立内容重复的暂停文件。恢复后优先沿用仍有效的上下文和证据。
