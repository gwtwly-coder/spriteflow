# 开发协作原则 v3.0

> 更新：2026-09-29。沿用 v2.2 文件名。本文件只定义稳定原则，具体执行以 `rc-runtime-policy-v2.2.md` 为唯一流程来源。

## 1. 成效优先

- 衡量交付质量、返工次数、用户操作量、总耗时和实际额度消耗；不以角色数量、文档数量、测试数量证明工作完成。
- 默认一个能够推进实现的主负责人。决策、开发、视觉调试可以由同一负责人连续完成；独立审查用于明确的高风险问题。
- 用户负责需求、审美取舍、重要范围与发布决定；负责人承担公开资料调查、日常调度、工具使用、明显缺陷修复和结果整合。
- 允许能力匹配的强模型直接施工。便宜模型只有在总体成本和质量合适时才优先。

## 2. 唯一事实来源

- 用户最新明确要求优先于本套模板；宿主规则与实际权限始终有效，不得假设提示词能开启未提供的工具。
- 产品方向以用户确认的交接文件及后续决定为准；代码、配置、运行结果是实现现状的证据，不能自行推翻产品目标。
- 运行流程、验收与安全标准只在运行协议中定义；主提示词负责授权和入口，使用说明负责教人启动。
- 资源以已核实记录为准，不以历史型号表为准。公开支持、账号可用、客户端接通、项目表现分别标记。
- 冻结的是经确认的产品决定。技术事实注明核验状态，设计参数区分建议与定稿；调整实现细节不必走重大变更流程。

## 3. 按风险裁剪

- 小修改：主负责人直接完成，验证相关行为并保留简短记录。
- 跨模块改动：明确接口、依赖和文件边界，再按需并行。
- 大改造：先做代表性路径和必要架构决策，验证后分批扩展，避免一次性铺开。
- 安全专项轮适用于所有项目；裁剪其检查项和深度，不能取消整轮。无对应攻击面的项可有证据地标注不适用。
- 已有效验收的方向、设计图和未受影响的验证结果可以复用。只有失效或存在真实风险时才重新检查。

## 4. 委派与所有权

本规则授权主负责人在工具和宿主允许时主动委派独立任务。子智能体是按需调用的工作能力，不等于让用户手动打开一个新窗口。

- 每个委派写清目标、输入、允许修改、禁止修改、依赖、验收和返回证据。
- 同一时间同一文件只安排一个写入者；共享入口、锁文件和样式基础由指定集成人处理。变更范围前先与负责人协调，保留现有未提交工作。
- 主负责人等待必要结果、处理冲突和集成验证。子任务完成不等于整个功能完成。
- 子智能体的模型选择、额度及工具支持以宿主实际能力为准，不假定能跨供应商调度或自动调用用户全部订阅。
- 高风险改动尽可能安排有相关能力的独立审查；不强制异模型家族。资源不足时标记独立复核缺口，不伪造双人验收。

## 5. 前端、测试与安全

- UI 图用来确定方向；真实页面负责证明结构、效果和交互可行。已有图不重新走生图流程。
- 视觉负责人对照实际渲染修正结构和效果，并提供项目内调节入口；不能让用户用调节面板替代开发者完成基本还原。
- 测试围绕明确风险和用户行为。只有新修改、失败、环境变化或证据不足，才扩大或重跑检查。
- 安全从设计开始考虑，另设一轮专项加固与验证。代码防护、部署防护和运行证据分别记录，不能用一项代替其他项。
- 不承诺零漏洞或无限抗压；交付应如实说明验证范围和剩余风险。
